## Stage 3 — real recent listening and recommended stations

`AutoHomeContent` projects up to eight newest distinct playable entries from the durable typed ListeningHistory log at the top of car Home/Music. A new user has no invented listening items; the existing owned-primary-player history recorder adds an entry only after actual playback. The service observes that log and the car feed cache and notifies subscribed browsers when content changes. History is read again after a first cold fetch to avoid publishing an old empty snapshot. Playback engines and the history writer are unchanged.

Phone Home's synthetic Recently played section also contains Liked Songs and saved playlists. The car keeps those as **From your library** shortcuts, removes cached track rows from that mixed section, and uses the real log for the top shelf. This avoids showing saved-but-unplayed playlists as history and prevents cleared history reappearing from the phone feed cache. Other sections remain scrollable on the same Home page. Deduplication uses typed stable IDs, not display names; a track stays a track and an episode stays an episode on the existing direct-audio path.

The new **Recommended stations** group uses only playlists actually returned under `Recommended stations` / `תחנות מומלצות` in the raw Spotify Home response already used by the application. It retains server order, playlist IDs and metadata, moves those cards above the other feed sections and removes exact duplicates below. Generic search-based Popular radio results are not relabeled as personalized stations. Empty/unavailable/unrecognized shelves produce no fabricated stations; other content still appears. Actual availability is account/server dependent and the private Home response is not a public stable API contract. The web integration's feed may differ from Spotify's Android Auto feed; identical personalized results are not claimed.

This uses the app's existing raw `Api.home` cache after loading the existing Home engine. On a disk-only cold cache it makes a bounded request through `provideHomeFeed`. It does not add a new radio generation algorithm or modify Spotify/YouTube/RSS clients. Spotify describes Radio as an updating artist/album/song-based collection that can be saved as a playlist ([official Radio documentation](https://support.spotify.com/us/article/spotify-radio/)); that establishes playlist semantics, not how the original car app privately ranks its home shelf.

The service-owned cache coalesces simultaneous Home/Music loads, keeps current content usable during refresh, bounds the first load, and uses a two-minute success TTL / 15-second failed-attempt retry interval. There is no timer polling or fetch on every progress event. Existing local history renders without waiting for remote loading. Failed refreshes preserve a previously usable snapshot; successful empty station data removes that shelf. Cancelling a browser callback does not cancel the shared load; service destruction cancels it and unregisters the history observer.

## Stage 1 implementation

`AutoPlaybackControls` removes advertised Previous (both Media3 variants), GET_TIMELINE and SEEK_TO_MEDIA_ITEM permissions for car presentation. This frees one transport slot for the existing three custom actions and stops exporting the public queue. The actual app queue, underlying one-stream player and manual next/repeat logic are unchanged. Seek-in-current-item, duration, position and metadata permissions remain available.

Media3 **1.3.1** builds the shared legacy framework PlaybackState and queue using the **media notification controller's** available commands. Changing only the Gearhead connection result is insufficient. `PlaybackService` therefore observes AndroidX `CarConnection` (pinned app library 1.4.0), filters that controller while projection/native car mode is active, and restores its original commands on disconnect. Direct car controllers also receive filtered permissions. The observer is removed at service teardown. The manifest adds visibility for the official connection provider. There is no autoplay on connection and no device-model check.

The legacy session is shared: system notification/lock-screen controls can reflect the car arrangement **during projection**. Standalone phone/Bluetooth previous/queue permissions return after disconnect. Phone Compose layouts do not change. The actual five-button positions and the host's decision to omit overflow still require DHU verification; no view hierarchy is being drawn by SpotUI.

Radio still requests recommendations for the exact current Spotify track, rejects episodes, missing identities, duplicate tracks and numeric-ID collisions, and preserves recommendation ranking. It now starts the top-ranked valid **new** track at position zero through the existing `SongPlayer.resumeResolvedPlayback` path. Only its successful source-preparation callback commits the station queue. No recommendation means no change to the current song/queue. Fetches are bounded to 15 seconds and preparation to 45 seconds. Ownership/queue/play-intent changes invalidate a stale fetch. Car Pause/Stop cancels the pending command; ownership changes, timeout/cancel and duplicate callbacks cannot publish a late station or stop a newer owner.

Save remains idempotent and uses the existing Liked Songs store/sync. Repeat remains OFF → ALL → ONE with the existing icons/state; no extra copy of these actions was added.

## Progress-bar boundary

The reference shows a thin passive-looking line while SpotUI's screenshot has a round seek thumb. Android Auto owns the progress view's thickness, padding, thumb and layout. Removing seek permission merely to hide a thumb would remove dragging functionality; this implementation deliberately **retains seeking**. It does not claim a pixel-identical progress bar, and makes no phone seekbar changes. Exact host rendering and whether the original supports dragging cannot be established from a still image.

Primary references: [Android playback actions and queue](https://developer.android.com/training/cars/media/enable-playback), [host-owned playback layout](https://developer.android.com/design/ui/cars/guides/app-types/customize-playback-controls), [CarConnection](https://developer.android.com/reference/androidx/car/app/connection/CarConnection). Exact 1.3.1 session / 1.4.0 connection sources were inspected from Google's Maven repository under the ignored report directory.
